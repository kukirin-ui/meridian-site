Meridian Family · what's new

What's new

Every release, newest first. All five apps are updated together and signed by one certificate. Download the latest release.

2.6.30Your own code in the Sandbox

  • Diagnose takes your own program: paste Python, C, C++ or JavaScript code (up to 5000 lines) and the output it should print. The Sandbox runs it as it is, then the fix templates and the models try to fix it, the same way they fix a practice case.
  • A fix counts only when a real run in the Sandbox prints exactly the expected output and exits with 0. Without an expected output your code runs once and you see what it printed and its errors; nothing is called fixed.

2.6.29Method typos and Go type bugs

  • Fix templates know the built-in method names of JavaScript, Python and Go, so a typo like toUppercase becomes toUpperCase on the first try. In Go, a number joined to a string becomes a string.
  • Diagnose's counters show the fixes made by models 1, 2 and 3 correctly.

2.6.28Type bugs fixed on the first try

  • Fix templates now handle type bugs: a number written as text ("3" - 1) loses its quotes, and in Python a text + number join gets str() around the number. These used to crash, fail to build or segfault until a model guessed the fix.

2.6.27Fixes on the skill tree

  • Every proven fix is now placed on the Code Master skill tree: the kind of error, the language and the patterns that fixed it each map to a skill (for example L-16 Debugging method, L-08 Algorithm design, L-13 JavaScript). The skills travel with the card into Meridian Core, in its intent, context and method form.
  • Diagnose shows how many proven fixes each skill holds, and a model working on a case now gets the skill card that kind of error calls for, next to its language card.

2.6.26Templates read the cards

  • Fix templates now use the proven cards in Meridian Core. A card whose wrong line has the same shape as a line in the new case (numbers aside) has its change tried first, so a bug the library has seen before is often fixed on the first attempt.
  • Cards that a template proved also seed what the templates learned, so the order of attempts starts from the library's experience instead of from zero.

2.6.25Two bugs at once

  • Fix templates now measure how close a wrong output is to the right one: matching words, and numbers by how near they are. Fixing one of two bugs moves the output closer, the search sees it as progress and builds the second fix on top, instead of throwing the half-fix away.

2.6.24Fix templates that learn

  • Every Sandbox run of a fix template now updates a success estimate for that pattern, per language and kind of error (wrong output, syntax, unknown name, import, type, crash). Templates are tried in the order of what has actually worked, so a kind of bug that took 7 tries the first time takes 2 the next.
  • Old results fade, so the order follows the bugs of now. Diagnose shows what was learned for each kind of error.

2.6.23Model 1 searches like the templates

  • Model 1 no longer bets on three big rewrites. It tries up to 12 small fixes, one line or one expression each, and the Sandbox checks every one as it arrives, stopping at the first that passes.
  • A fix that crashes the program is reported as a crash, with its error line, instead of as wrong output.

2.6.22Templates and models work together

  • When fix templates get part of the way (a build error fixed, one of three faults gone), the models start from that program and its real remaining error instead of the original.
  • Every failed step says why: no answer in time, no change, does not build, or wrong output.
  • A language whose tools are missing, such as TypeScript without tsc, is left out of the run instead of failing every few cases.

2.6.21The models stop timing out

  • Parallel gives the models one case at a time. Fix templates still work on three cases at once, but a local model answers one request at a time, and three cases queued up on it ran out of time while they waited.
  • A model stops writing by itself before its deadline, so an answer that is given up on no longer blocks the model for the next case.
  • A model with Thinking on gets a thinking budget it can finish on a phone.

2.6.20A generator that does not repeat itself

  • Parallel's generator remembers every case it made, across runs. A case it has seen before is made again with a new seed, and when a size has nothing new left (the 1-line programs run out fast) it moves up a size by itself, so cases get harder instead of repeating.
  • The status line says what is happening now: templates, model 1 starting and writing fixes, the debugger, 2 or 3, instead of showing the last template count while a model works.
  • The Sandbox shows its real 4 sessions.

2.6.19Models 1, 2, 3 and four new recipes

  • Chat's Tweaks has a model board instead of the system picker: three slots on top show which models are 1, 2 and 3 and whether they run, and every model in the list has its own 1 2 3 boxes and an × to take it off the list (the file stays).
  • The fix pipeline reads 1 → 2 → 3: model 1 writes three fixes, 2 looks at the best failed one with the debugger's view, 3 decides last. Parallel's counters and steps use the same numbers.
  • The knowledge pack gains four proven recipes (Vanguard IOMMU BSOD, phone inference battery drain, local vision in Termux with llama.cpp mtmd, OpenStick EDL backup) and one unreviewed note. Every fix card now carries its intent, context and method, and small models get that form when the whole card would not fit.

2.6.18Every model on the phone, the fix library in Chat

  • Chat now finds model files anywhere on the phone: Termux, all of the phone's storage and SD cards. A listed model whose file was moved is found again by itself instead of being called missing.
  • Chat's menu has a Fix library with the live count of proven fixes by language and the latest cards, each in its ICM form.
  • Gaming's dashboard rings are made of glowing ticks, lit from cyan to violet up to the value, around a raised glass centre, with glowing tiles, a gradient memory bar, a grid behind the live graphs and an edge-lit main card.

2.6.17Steadier builds

  • The build server now retries a cut-off Android SDK download up to three times, so a network glitch no longer stops a release.

2.6.16A new Gaming dashboard

  • Gaming's dashboard has gradient rings with an icon in each (storage, network, CPU, GPU, RAM, battery), stat tiles with icons and live clock graphs that fade into the card.

2.6.15Focus for the models

  • Chat's Tweaks has Focus, Gaming's Isolate for the models: every running app is stopped through Core except Termux, the Meridian apps, what Android needs and Google Play services, and the RAM it gave back is shown. It can also run by itself before the models load.

2.6.14Cards that teach

  • Core now keeps every proven fix in one ICM form (intent, context, method), whichever app found it.
  • The fixer gets up to 3 matching proven fixes and the helper and judge up to 5, the most-found first, so the models learn from the library as it grows.
  • CPU clusters apply to the model chosen in llama.cpp settings (each model keeps its own), and a check shows the cores each running model really uses.

2.6.13The fix ladder

  • Diagnose now fixes in up to three steps, each a model you pick: the fixer writes three candidates; if none passes, the helper looks at the problem anew; if that fails, the judge weighs both attempts and writes the last fix. Every fix that passes the Sandbox becomes a card in Core's library.
  • Before each next step, Parallel's Debugger runs the failed attempt under the real debugger (pdb, node inspect, lldb or gdb) and hands over the call stack and variables at the line that matters. Bash gets a bash -x trace.
  • Every model in use has its own full llama.cpp settings, and the cards in Tweaks fold away.
  • The Sandbox runs 4 jobs at once instead of 2, so cases no longer queue behind each other.

2.6.12The fixer sees what the program did

  • When the fixer's attempts fail, its second try now gets a trace of the failed attempt: for Python the variables that changed on each line, for Bash every command with its real values. Logic bugs print no error, so this shows the model what actually happened.

2.6.11Parallel wakes the models

  • When Chat's fixer or reader is not running (after a speed test, a Fit check or a Termux restart), Parallel's Diagnose starts it again by itself with the exact settings Chat last used, then asks again. No more "Failed to connect" failures in the generator.
  • When the fixer is another model than the one that answers, Tweaks › llama.cpp settings lets you edit the fixer's own settings.
  • Model lists show the quantization (Q4_K_M, Q8_0), so two files of the same model can be told apart.

2.6.10Counters you can reset, failures you can read

  • Parallel's generator has Reset counters, and a Last failures list that says why each case was not fixed, with Copy failures.
  • Core's Settings › Knowledge now shows the fix library: every fix the Sandbox proved, by language and by where it came from. Cards arrive by themselves; Plan and Diagnose search them.
  • JavaScript errors are named by their real error line, not by Node's version line.
  • Chat no longer passes draft tokens to llama-server when no draft model is set.

2.6.9Settings that take effect

  • When the fixer, the reader or the model that answers is running with older settings than the ones shown in Tweaks, Chat says so and offers Restart with the new settings, so a change never silently waits for the next load.

2.6.8Model lists that match the phone

  • In Tweaks, every model picker (the model that answers, Reader, Fixer) also offers the .gguf files found on the phone that are not in the list yet; picking one adds it.
  • Models whose file is no longer on the phone are marked, and one tap removes them from the list (the files themselves are never deleted).
  • Tweaks looks for models once each time it opens, so the lists stay current.

2.6.7Two-model pipeline

  • Pipeline in Chat's Tweaks: pick a small reader model and a fixer. Chat runs the reader as a second llama-server; both stay in memory but never compute at the same moment.
  • Diagnose now goes fix templates → reader → fixer. The reader answers in a fixed JSON shape (which file, which lines, what kind of fault, one sentence on what is wrong); the fixer gets only that region and the matching cards. If the reader is slow or off, the old path is used.
  • The Generator counts fixes by template, by model with the reader and by model without it, so the difference shows in numbers.
  • Speed test is back in sight: on the Local model card, and "Test both" for the reader and the fixer.
  • Fit check runs its full memory test again.

2.6.6Repair that works on a phone

  • Fix templates: Diagnose first tries known fix patterns at the spot the error points to (a misspelled name, a wrong operator, off by one, a missing bracket or keyword, an inverted condition, a missing import), in all 10 languages. Every attempt runs in the Sandbox; no model is needed for these.
  • When the templates don't find it, the model answers in a fixed JSON shape with whole functions (llama-server enforces the shape), thinking is off for repairs, up to 3 candidates are tested, and the best failed one goes back with its new error once more.
  • Everything starts at 1 line: the generator writes tiny real programs (1, 5, 10, 25 and 50 lines) in every language, and Diagnose and Code on request take 1 to 5000 lines.
  • Code on request checks the tests first: tests that don't even run are repaired before they are locked, so a broken test can't block the program.
  • The Generator shows how many cases were fixed by templates and how many by the model.

2.6.5The generator

  • Generator in Parallel's Diagnose: writes real programs in 10 languages (Python, C, C++, JavaScript, TypeScript, Bash, Go, Rust, Lua, Ruby), from 100 up to 5000 lines, puts 1 to 3 faults in them and runs them in Termux for the real error. With Auto feed on, every case goes to Diagnose by itself.
  • Sandbox: every fix Diagnose makes is tested on a copy of the whole program, with time and memory limits, 2 sessions at once. A fix counts only when the program's own self-test gives exactly the same output as before the fault.
  • Every proven fix becomes a card in the new library in Meridian Core, shared by Chat, Parallel and NullCloud, with duplicates merged, so every app learns from it.
  • Code on request: describe a program and the model writes it with tests; the Sandbox runs them and Diagnose fixes failures. Up to 5000 lines, written in tested parts above 1000.
  • An ICM router hands the model only the cards that fit: proven fixes first, then the one skill card for that language, never loosely related filler. Plan and Chat use it too. When a skill card changes, the Sandbox re-runs the programs that used it.

2.6.4Tweaks

  • Chat's Tweaks page now holds everything about the local models: the model that answers, its llama.cpp settings, advanced llama-server options (memory lock, MoE experts on CPU, thread priority, cache reuse, sampling, a draft model), and the list of models with speed tests and downloads.
  • Temperatures come from Android's thermal service through Core, so CPU, GPU, battery and skin readings show on phones that hide their sensors. Heat Guard goes up to 65 °C for the battery.
  • A model you chose stays: when its context is full, Chat gives it a bigger context instead of switching to another model.
  • Ask about this phone now answers with the readings and your own speed tests, not a guess.
  • Local models and Cluster left the menu; the connection button is back in the right corner.

2.6.3Clusters: where the model runs

  • On Chat's Phone page, CPU clusters only choose where the local model runs: tick the clusters and Termux starts llama-server on those cores (taskset). No root needed.
  • The cluster limit sliders are gone.

2.6.2Chat's Phone page

  • Phone in Chat's menu is now one page: the phone and its chip by the names Android reports, every temperature sensor (read through Core), memory, the model that answers and all of its llama.cpp settings with sliders. Fit check opens from there.
  • Heat Guard pauses the local model when the battery, CPU, GPU or AP reaches its limit; Safeguard lets it continue once everything has cooled down.
  • CPU clusters as the kernel lists them: tick the ones the model runs on. With root through Core you can set each cluster's limit. Core itself now shows only the number of clusters.
  • Replies now sit in a bubble. The model button left the header, and Settings keeps only look and feel.
  • New connectors: GitHub (add a file from a repository to your message) and Hugging Face (a token for gated models), next to Web search.
  • Gaming's number settings got the same sliders.

2.6.1Reconnect finds the new port

  • Wireless debugging gets a new port every time it is turned on, and Android can still report the old one first. Core tried that old port, was refused and gave up, so Reconnect did nothing.
  • Core now reads the current port from Android when it is allowed to, and otherwise tries every port Android reports on this phone until one answers. After you turn Wireless debugging back on, Reconnect works without pairing again.
  • Turning Wireless debugging off still stops Core's helper on some phones (seen on a Galaxy S26); only root could prevent that. Leave it on: it is encrypted and needs your pairing key.

2.6.0Core stays connected

  • 2.5.9 switched Wireless debugging off once Core's helper was running. On a Galaxy S26 that stopped the helper, so Core asked to reconnect and Gaming showed it as not started. Core now leaves Wireless debugging as it is: it is encrypted and needs your pairing key.
  • Port 5555 (adb tcpip) is still handled: on a rooted phone Core closes it to the network once it is connected; without root Core warns you to run adb usb. The setting is now called Close port 5555 after connecting and always shows what is saved.
  • One Core screen: the link to the old classic Core screen is gone, so Core no longer has three different menus.

2.5.9Clear jobs for every app, a safer Core

  • Every app now knows what this phone allows: Core's helper, root, or neither. Settings the phone cannot run are hidden, not shown greyed out.
  • Gaming's tweaks run through Core's helper, the same way Chat's did. Before, Gaming sent some of them to Termux, where they did nothing. Gaming no longer needs Termux at all.
  • The apps share data through Core on checked channels: only the app that owns a piece of data can change it, and Core checks every write.
  • Core closes the debugging port once it is connected: Wireless debugging is switched off, and on a rooted phone port 5555 is blocked from the Wi-Fi. Without root, Core warns you to run adb usb. You can turn this off in Core's settings.
  • One place for each thing: Settings is the gear at the top of every app. Chat no longer carries a copy of Gaming's tweaks; change them in Gaming.
  • Removed what had no place: Parallel's hidden mesh, and Gaming's model benchmark, Vulkan driver switch and agent (models belong to Chat).

2.5.8Two clear ways to connect Core

  • Core's pairing sheet now has two buttons: Wi-Fi debugging (pairing, unchanged) and USB debugging (adb tcpip 5555, then Connect over USB).
  • USB: Core no longer asks "Allow USB debugging?" at launch and gives up before you can answer. A tap on Connect over USB is never lost, and after you allow it Core connects again by itself.
  • Chat: no flicker and no jumping after Apply, Load or Add. The screen stays where you left it.
  • Chat: Phone tweaks are compact, one line each, with the choice and Apply side by side.

2.5.7USB route fixed, Tweaks back in Chat

A tester on a Galaxy Z Fold4 found that the USB route from 2.5.6 could not be used. Thanks, Tamara.

  • Core's page refreshes every 2.5 seconds, and it rebuilt the pairing sheet each time. No Wi-Fi? Connect over USB instead closed within a second, and the message under the button vanished.
  • The pairing sheet now stays as you left it: folded parts stay open, and a typed code stays typed.
  • After Connect over USB, the line under the button follows Core live: Core's own reason if it fails (for example, nothing answers on port 5555), or Connected over USB, after which the sheet closes.
  • Chat › Local models › Settings for this model has Phone tweaks again: clusters, GPU, heat, memory and Release RAM, the same tweaks as Meridian Gaming, through Core and without root. Every command is shown before you approve it.
  • The model's number fields (threads, cores, context, GPU layers, batch, micro batch, max reply) now line up two per row. A label that wraps no longer pushes its field out of line.

2.5.6Core connects without Wi-Fi

Wireless debugging needs Wi-Fi, so a phone without working Wi-Fi could not start Core's helper. Now there is a second way.

  • Core's pairing sheet has No Wi-Fi? Connect over USB instead: run adb tcpip 5555 once from a computer or another phone over USB, then tap Connect over USB.
  • Core connects to the phone itself (127.0.0.1). The first time, Android asks "Allow USB debugging?"; tick Always allow.
  • Pairing over Wireless debugging works as before, and phones that are already paired connect exactly as before.

Security: while adb tcpip 5555 is on, the phone also listens on port 5555 toward the network. Android still asks before it trusts a new key, so never confirm "Allow USB debugging?" unless you started it yourself. A restart turns it off.

2.5.5The Merge review in Core

  • Core › Settings › Knowledge shows the learned cards the apps share and how many are verified on this phone.
  • Cards that say the same thing are joined by themselves. Cards that only look alike wait for you: Merge or Keep both, and a pair you kept apart is not asked again.
  • Once a day, one quiet notice when pairs look alike. It only counts; it never changes a card. It is off when Notices are off.

2.5.4Diagnose reads the real system, and the apps share what they learn

  • Parallel's Diagnose can read how a failing program is built on your phone: its package, the libraries it loads, its dependencies and whether their files are intact. Read-only, and shown before it runs.
  • The old pattern engine now only gives weak evidence. The model-based engine decides, and a repair is offered only after a read-only check confirms it.
  • When a repair is verified (the check failed before and passes after), Parallel saves a learned card. The next time the same failure appears, the card is suggested; if a fix stops working, the card is marked failed.
  • Learned cards sync between the apps through Core, card by card, without losing changes. Each app still works alone; Gaming keeps only gaming cards.

2.5.3Diagnose checks code

  • Paste code into Diagnose and it is checked, never run: Python, JavaScript, C, C++, shell, SQL, JSON, YAML and .env.
  • Each finding shows its line and where it came from: the language's own tool, or a known-mistake pattern.
  • A Beginner and a Technical view, and a missing checker (like pyflakes) is offered as a labelled step with what it changes, the risk and how to undo it.
